# Spec for firebase-signup-codename
branch: claude/feature/firebase-signup-codename
figma_component (if used): N/A

## Summary
Wire the existing signup form (`AuthForm` in `mode="signup"`, rendered at `app/(public)/signup/`) to real Firebase Authentication, replacing its current `console.log`-only submit handler. On successful account creation, generate a random "codename" — built by picking one word from each of several distinct word sets and joining them together in PascalCase — and set it as the new user's `displayName`. Also create a document in a Firestore `users` collection storing the codename and the user's id, explicitly excluding their email. Only the Firebase Web (client) SDK is used, exported from `lib/firebase.ts` — no Firebase Admin SDK or server-side auth code.

## Functional Requirements
- Submitting `AuthForm` in `mode="signup"` creates a new Firebase Auth user with the entered email and password, using the client Firebase Web SDK (via the existing `auth` export).
- On successful account creation, a "codename" is generated by selecting one word from each of multiple distinct, non-overlapping word sets and concatenating the chosen words together with no separator, each capitalized (PascalCase) — e.g. two sets like adjectives and nouns producing something like `CrimsonOtter`.
- The generated codename is set as the new user's Firebase Auth `displayName`.
- A document is created in a Firestore `users` collection for the new user, storing the codename (as `codename`) and the user's id. The user's email must NOT be written to this document.
- Only the Firebase Web SDK (`firebase/auth`, `firebase/firestore` client APIs, as already configured in `lib/firebase.ts`) is used for this flow — no Firebase Admin SDK, no Next.js server actions/API routes performing the signup.
- The existing `AuthForm` markup, styling, and password-visibility toggle are unchanged; only the signup submit behavior changes from logging to performing real Firebase calls.
- `AuthForm`'s `mode="login"` behavior is unaffected — this spec covers signup only.

## Possible Edge Cases
- Firebase Auth rejects the signup (e.g. email already in use, weak password, malformed email) — the user needs a clear indication that signup failed.
- The Auth user is created successfully, but setting the `displayName` or writing the Firestore `users` document afterward fails — this leaves an inconsistent state (an auth account with no codename and/or no Firestore record) that needs a defined handling strategy.
- Two different signups could theoretically land on the same word combination, since the word sets are finite — whether this is acceptable or needs to be prevented is an open question below.
- Rapid double-submission of the form (e.g. double-click) should not create two accounts or two Firestore documents for one signup attempt.
- The signup form's client-side `required` HTML5 validation doesn't guarantee a Firebase-valid email/password — Firebase's own validation errors still need to be handled.


## Acceptance Criteria
- User can successfully sign up with email and password using the existing SignupForm component
- A Firebase Auth account is created with the provided credentials
- The Auth user's displayName is set to a randomly generated PascalCase codename
- A document is created in Firestore's 'users' collection containing only codename and id fields
- Error messages are displayed for invalid input or Firebase errors
- Loading state is shown during the signup process
- User is redirected to /heists page after successful signup
- Email address is NOT stored in the Firestore users collection

## Open Questions
- Should the word sets for codename generation be stored in a separate utility file or inline? New file.
- What should happen if Firestore document creation fails after Auth account is created? (Retry, log error,
show warning?) log the error.
- Should we validate that the generated codename is unique in Firestore before assigning it? No.
- What specific Firebase Auth error messages should we display to users vs generic error messages? Password strength error, email errors, you decide

## Testing Guidelines
Create a test file(s) in the /tests folder for the new feature, and create meaningful tests for the following cases, without going too heavy:
- Codename generation produces valid PascalCase strings from three word sets
- Codename generation returns different values on multiple calls
- Signup form successfully creates Firebase Auth account with valid credentials
- User profile displayName is updated after account creation
- Firestore document is created in 'users' collection with correct structure
- Error handling displays appropriate messages for common Firebase Auth errors (weak password, email already in use)
- Loading state is shown during async operations
